# LogConvention: ELF Logging Standard

The rules every human and AI agent in an ELF project follows for writing experiment logs, saving result files, and handoff.

How to read it: §0 summarizes the judgment rules that apply to every trial; autoread adds it at session start and after a context rebuild. Each section puts the judgment rules (what the agent and the user decide) first and "What the tool does" (what elf commands write or check) after. Command details come from the command output and `elf <command> --help`.

---

## 0. Core summary

Only the judgment rules for every trial. Items already in the `AGENTS.md` standing duties (phase separation, immediate figure embedding, session lifecycle, deprecation, avoiding hand edits of logs, etc.) and formats that the tool writes or checks are left out. A trailing § points to the details. The body prevails over this summary.

- **S or G**: work on its own output = S; a change to rules, structure, templates, or tool settings for all later work = G (§1)
- **Log content**: facts only (parameters, results, errors and fixes). Ideas in `1_Concept/13_Ideas/`, multi-session plans in `1_Concept/12_Planning/` (§1)
- **goal, handoff, conclusion, user_note**: goal = the session goal in 1-2 sentences. handoff = `valid conclusions; pending …; refs …`, rewritten whole, no history. conclusion = the valid final conclusion at close. user_note = the user's own words only (§2)
- **Style**: short list items, no paragraphs. Move hypotheses over 5 items or reasoning over 5 steps to `1_Concept/12_Planning/` (§2)
- **Figure pre-registration**: a figure-producing trial lists its expected outputs in Prediction (§2)
- **Refinement**: regenerating a working output with new parameters or looks = the next trial (delta and reason in Conditions); keep scripts and figures versioned (§2, §3.3)
- **Initiator and rejected alternatives**: `raised by the user` or `proposed by the AI` in Background, else Goal. A path rejected at entry = Background, scope exclusion = Conditions, rejected by results = Interpretation and Lessons (§2)
- **Rule change**: written in a G trial; an affected S trial gets one line `- Rule change: G004 t03` in Conditions (§2)
- **File names**: outputs `S{NNN}_…`, `S{NNN}_t{NN}_…` when trials must be told apart (§3)

## 1. Log File Location & Naming

For documents other than logs (planning documents, etc.), follow the folder rules in `.elf/managed/AI_PARA_Framework.md`.

| Item | Rule |
|------|------|
| **Which series** | Work that applies only to its own output = an S trial; a change that applies to all later work = a G trial. G = changes outside the research content such as rule edits, structure changes, templates, tool settings |
| **Content rule** | Record only facts (a fact sheet): simulation parameters, run results, errors and fixes |
| **Prohibited** | Ideas, planning, and direction discussions go to `1_Concept/`, not `2_Log/`: small ideas in `13_Ideas/`, multi-session plans in `12_Planning/` |
| **Wiki** | `2_Log/Wiki/` = knowledge documents that span sessions (topic pages). Not part of the session-close procedure; updated in a G session after user approval |

### What the tool does
- Logs live in `2_Log/S/` (research) and `2_Log/G/` (governance) and are never moved. The state is only the header `status` (`ongoing`, `complete`, `deprecated`).
- `Registry.md` (the session list) and the explorer settings in `.vscode/settings.json` are generated by elf from the headers; do not edit them.

## 2. Log Format

The section names, their order, and what each section holds live in one place: `.elf/managed/templates/trialTemplate.md` (elf creates and checks trials from it). The overall shape of a log:

```markdown
---
created: YYYY-MM-DD
modified: YYYY-MM-DD
status: ongoing
goal: '{1-2 sentences on the session core goal}'
handoff: '{current state; pending work; references}'
conclusion: ''
user_note: ''
---
# S{NNN}: {session title}

<!-- ELF norm comment (inserted by elf) -->

## t{NN}: {task title}
(body = trialTemplate: optional Background; Phase 1 Goal, Conditions, Hypothesis, Prediction; Phase 2 Observation, Interpretation, Lessons, Files)
```

### Header rules
- **goal**: 1-2 sentences on the session's core goal.
- **handoff**: a replace-style state snapshot in three `;` parts: `valid conclusions and where they are (e.g. "A rejected, B adopted"); pending; references (the synthesis trial)`. Rewrite it whole; do not list history or completed steps (details belong to the trials). `;` only separates parts: use commas inside a part, and start the pending and reference parts with their labels (`pending`, `refs`). On handover or after a context rebuild, read the front matter (`Read(offset=0, limit=9)`) to restore the state.
- **conclusion**: the final conclusion at close (the currently valid result).
- **user_note**: the user's own thoughts at close (decisions, next steps, remaining uncertainty). **The user's own words only**; the agent never invents or summarizes them (keeps the user's judgment apart from the agent's reading). `''` when skipped.

#### What the tool does
- Only elf commands write the header (7 YAML keys): goal = `elf session new --goal`; handoff = the YAML block at the top of the `--from` file of `elf trial new`, `elf trial write`, `elf session close`; conclusion and user_note = `elf session close --from` (§5.1, §5.2). In a `--from` file, wrap values in single quotes and write a `'` inside a value as `''`.
- Values per status (checked by `elf check logs`): `ongoing` = conclusion and user_note `''` / `complete` = conclusion required / `deprecated` = the deprecation reason and replacement in handoff (§6).

### Body rules
- **Writing language**: write in the `PROJECT_LANG` language (EliRule §3), in short list items rather than paragraphs.
- **Section heading form**: section headings follow the deployed trialTemplate (`### Goal`, `### Conditions`, …). Logs written before 3.4 may carry the older bilingual headings (the Korean name first, the English name in parentheses); elf reads both forms as the same section and writes new sections in the English form.
- **Inline figure embedding (plot = trial output)**: in the turn a figure is produced, embed it in that trial's `### Observation` as `![alt](path)`, with the figure number and a one-line description (axes, key observation) in the alt text. Postponed figures get lost or end up in the wrong trial. Not allowed: a path in a table only, postponing for confirmation or feedback (embed v1 at once and update it), showing it in the chat or a viewer instead. Figures made by a delegated worker (sub-agent) are embedded by the main agent at merge time (delegation does not lift the duty).
- **Pre-register expected outputs (Phase 1)**: a trial expected to produce figures lists them (figures, tables) in `### Prediction`; each item is embedded the moment it is created. No "draw everything, tidy up later" plan (it is lost at a context rebuild). An unexpected figure is embedded at once too, with the difference from the prediction noted in `### Observation`.
- **Reminder hook (recommended)**: when the harness (agent runtime) offers tool hooks, add a hook that reminds about embedding right after a figure is made. Example: a Claude Code PostToolUse hook that detects new images in `6_Exp/64_Viz/` after a shell command.
- **Refinement (base-delta trial)**: regenerating a working output (figure, table, data) with new parameters or looks (font, color, size, axes, style) is the next trial, even once: `### Conditions` holds base = the previous trial and the delta with its reason (the problem with the previous attempt); `### Observation` holds that version's figure. Keep scripts and figures per version (§3.3). Do not fix things quietly and report only the final result (against survivorship bias: record each version in its turn so failed attempts stay reproducible). Only debugging before an output exists and fixes that do not change how the output looks (typos, paths, comments, variable names) go in the same trial's `### Trial-and-Error` table.
- **Files table**: type (`Script`, `Output`, `Figure`, `Config`, etc.) and the path relative to the project root.
- **Code and parameters**: code in code blocks; parameters as a table of name, value, unit.
- **Hypothesis and Prediction (Phase 1)**: written before the run (a hypothesis fitted to results tests nothing). Short list items, no paragraphs, quantified where possible. Over 5 hypotheses or 5 reasoning steps: move them to `1_Concept/12_Planning/` and leave a one-line cross-ref.
- **Observation (Phase 2)**: written after the run. A prediction-versus-observation table is recommended.
- **Interpretation first line**: one of `Prediction match: match / partial / mismatch` (older logs may carry earlier labels; they stay valid). The line checks prediction against result at a glance; the mechanism follows from the second line.
- **Where follow-ups go**: no next-session-candidates section (one in an older log stays valid). While active = the pending part of handoff; at close = conclusion; across sessions = `1_Concept/12_Planning/`.
- **Background section (optional)**: only when the context exceeds the goal (prior-session synthesis, several inputs), 1-2 lines above `### Goal`. No empty background.
- **Initiator**: name who started the work or a pivot in Background (else Goal) in one word (`raised by the user` / `proposed by the AI`). When a user statement is the basis of the work, it may be quoted in Background (an in-progress opinion). The user's thoughts at close go in the header `user_note`.
- **Rule-change reference (S trials)**: when a rule or structure changes during research, write the change in a G trial and leave only one line `- Rule change: G004 t03` in the affected S trial's `### Conditions` (the reason lives only in G).
- **Rejected alternatives (by timing)**: a path rejected at entry = `### Background` (one line, no Phase 1 edits afterwards); scope exclusion = `### Conditions`; rejected by results = `### Interpretation`, `### Lessons`. Do not gather them into Background later (no rationalization after the fact).
- **Canonical rules over precedent**: past session and trial logs are reference material, not the norm. The norm = this document and `.elf/managed/templates/` (sessionTemplate, trialTemplate). When a precedent differs, follow the canonical rules and tell the user (a deviation copied from precedent spreads). Without the CLI, copy the trialTemplate to write a body (headers and Registry.md need elf).
- **Retroactive policy**: a rule applies to what is written after it takes effect; earlier records are not rewritten (they keep the basis of past decisions). Header format and location are changed by the `elf update` migration (§7).

#### What the tool does
- `elf trial new` numbers trials (G too; reference form `G004 t03`). Image path = `../../6_Exp/64_Viz/S{NNN}/file.png` (from the log folder; fixed because logs never move).
- Before writing, `elf trial new --from` and `elf trial write` check section names and order, required sections, the interpretation first line, template text, and missing figure embeds; `elf check logs` audits hand edits by the same rules. Intentional exclusion = `<!-- noembed: file.png -->`.

## 3. Result-File Saving Rules

### 3.1 Scripts

| Kind | Location | Name |
|------|----------|------|
| Simulation script | `61_Sim/Scripts/` | `S{NNN}_sim.m` |
| Post-processing script | `61_Sim/Scripts/` or `63_Analysis/Scripts/` | `S{NNN}_postProcess.m` |
| Helper function | `61_Sim/Scripts/` | `{function_name}.m` |
| Analysis code | `63_Analysis/Scripts/` | `S{NNN}_analysis.m` |

### 3.2 Data

| Kind | Location | Name |
|------|----------|------|
| Simulation results | `61_Sim/Data/S{NNN}/` | `S{NNN}_sim_results.mat` |
| Graphs | `61_Sim/Data/S{NNN}/` | `S{NNN}_Fig1_*.png` |
| Measured original | `62_Empirical/Raw/` | Read-Only |
| Processed data | `62_Empirical/Processed/S{NNN}/` | `S{NNN}_t##_processed.csv`, etc. |

### 3.3 Naming Rules
- Simulation results: `S{NNN}_{trial}_{description}.mat`
- Graphs: `S{NNN}_{description}.png`
- When scripts must be told apart by trial: `S{NNN}_t{NN}.m`, `S{NNN}_t{NN}_postProcess.m`
- **Keep refinement versions**: do not overwrite scripts and figures; keep a version suffix (`S{NNN}_A06a_*` → `_A06b_*`, or `_v1`, `_v2`). One version per delta trial. Overwriting loses the intermediate versions and the work cannot be reproduced.
- **core + wrapper**: instead of copying the whole script per version, split it into a shared core (taking the variations as parameters) and a thin wrapper per version (that version's delta parameters). Example: `S{NNN}_A06_core.m` + `S{NNN}_A06{a..}_plot.m`.

### 3.4 Visualization

| Kind | Location | Note |
|------|----------|------|
| Auto-generated figures | `6_Exp/64_Viz/` | Saved by scripts. The figure index `_gallery.md` is generated per session by `elf gallery` |
| Paper figures | `7_Paper/71_Figs/` | rawFig → processedFig → finalFig |

## 4. Cross-reference Rules

Logs stay in `2_Log/S/` (G in `2_Log/G/`), so relative path depths never change.

| From | To | Relative path (from `2_Log/S/`) |
|------|----|----------------------|
| Logs → Planning | `1_Concept/12_Planning/P00x.md` | `../../1_Concept/12_Planning/P00x.md` |
| Logs → Sim Data | `6_Exp/61_Sim/Data/S{NNN}/` | `../../6_Exp/61_Sim/Data/S{NNN}/` |
| Logs → Viz | `6_Exp/64_Viz/S{NNN}/` | `../../6_Exp/64_Viz/S{NNN}/` |
| Logs → same-series log | `2_Log/S/S{NNN}_log.md` | `S{NNN}_log.md` |
| Logs → other-series log | `2_Log/G/G{NNN}_log.md` | `../G/G{NNN}_log.md` |
| Logs → Wiki | `2_Log/Wiki/x.md` | `../Wiki/x.md` |
| Scripts → Data | `../Data/S{NNN}/` | `../Data/S{NNN}/` |

Content moved to Planning is marked in the original log with a blockquote stub:
```markdown
> Details were moved to a Planning document.
> - [P00x_Title.md](../../1_Concept/12_Planning/P00x_Title.md) — see section N
```

### What the tool does
- `elf check logs` finds broken relative `.md` links. The tool recomputes links only when it moved the files itself (migration); people and agents fix other broken links.

## 5. New-session Checklist

When an AI agent starts a new session:

- [ ] Research = `elf session new "<title>" --goal '<goal>'` (`2_Log/S/`); governance (rules, structure, templates, tool settings) = `elf session new --gov "<title>" --goal '<goal>'` (`2_Log/G/`). Several sessions may be ongoing (one session per task for parallel work; with several, pass `--session` to trial commands). goal = the session's core goal in 1-2 sentences (§2)
- [ ] If a preceding session is continued, read its handoff and conclusion and reflect them in the new trial t01's `### Background` / `### Hypothesis` (write the session id in Background)
- [ ] Create `6_Exp/61_Sim/Data/S{NNN}/`, write scripts `6_Exp/61_Sim/Scripts/S{NNN}_*.m`, save the .mat and .png results after the run
- [ ] Add a trial (t{NN}) to the log: parameters, results, image paths (§5.1)
- [ ] When a script is done: one-off scripts go to `Scripts/Archive/`, general ones stay at the root
- [ ] If planning content creeps in, move it to `1_Concept/` with a cross-reference

### 5.1 Trial Standard Operating Procedure (Phase 1 / Phase 2 split)

A trial (t{NN}) is written in two phases. **A stop between Phase 1 and Phase 2 is mandatory**: it prevents improvised runs and completes the hypothesis-observation cycle.

Logs are written only with the commands below. Keep hand edits to typos in content sections (`elf check logs` audits the structure).

| Step | Command |
|---|---|
| Start (first Phase 1 write) | `elf trial new "<title>" --from <Phase 1 file>` (G session: `--session G{NNN}`). Without `--from` it appends only the Phase 1 template (for writing in an editor) |
| Revise Phase 1 (during user review, any number of times) | `elf trial write [tNN] --from <Phase 1 file>` |
| Run after approval, results | `elf trial write [tNN] --from <Phase 2 file>` |

Without tNN, the last trial of the ongoing session is used. A YAML block at the top of the file (only key: `handoff`) replaces the header handoff. One file holds the sections of one phase only.

**Phase 1 — before the run (stop point)**
- [ ] (optional) `### Background` — only when the context exceeds the goal: entry intent, **initiator**, one line on a path rejected at entry
- [ ] `### Goal` (the task's what), `### Conditions` (parameters, constraints), `### Hypothesis` (3-5 suspected mechanisms or effects, short items), `### Prediction` (1-3 concrete results, quantified where possible; a figure-producing trial lists its expected outputs — §2)
- [ ] Run `elf trial new "<title>" --from <file>`
- [ ] **Stop** — show Phase 1 to the user and get confirmation. Put "t{NN} Phase 1 awaiting user confirmation" in the pending part of handoff. Apply requested changes with `elf trial write --from`. An AI in auto mode keeps this stop too

Example `--from` file (the top YAML block is optional):
```markdown
---
handoff: 'state = …; pending = …; refs t03'
---
### Goal
- …
```

**Phase 2 — after the run**
- [ ] Run the trial (script, simulation, research, etc.) after the user approves
- [ ] Right after the run, check `6_Exp/64_Viz/S{NNN}/` for this trial's figures and embed them in `### Observation` before leaving the turn (§2)
- [ ] `### Observation` (facts and a prediction comparison table), `### Interpretation` (first line = prediction match, then the mechanism), `### Lessons`, `### Files`
- [ ] If a working output was regenerated with new parameters or looks, continue in the next trial (delta) (§2, §3.3)
- [ ] Run `elf trial write [tNN] --from <file>`

#### What the tool does
- When a pre-write check fails, all problems are reported at once and nothing is written. Revising Phase 1 after Phase 2 exists, or after outputs appeared following the last Phase 1 write, is refused (a change that reflects results = a new trial). Rewriting Phase 2 is refused too (a rerun = a new trial).
- Exact synonyms of section names and of the interpretation label are corrected with a notice. A tool comment under the trial title records the Phase 1 and Phase 2 write times and counts.

### 5.2 Session-close Standard Procedure

- [ ] **Run `elf check logs` and resolve the warnings** (missing embeds, structure violations) or state intentional exceptions (`<!-- noembed: file.png -->`)
- [ ] Clean up handoff: finish the pending part or move it to a `12_Planning/` document (`elf session close` warns if it remains)
- [ ] The agent drafts the conclusion (the currently valid final result, no history)
- [ ] Show the draft to the user for **approval** and ask for the user's own note (`user_note`) — the user's words only; empty if skipped
- [ ] Write the close file and run `elf session close --from <file>`

Example close file:
```markdown
---
conclusion: '…'
user_note: '…'
handoff: ''
---
```

#### What the tool does
- `elf session close --from`: allowed keys = `conclusion` (required), `user_note`, `handoff`. It sets status to `complete` and regenerates `Registry.md` and the explorer settings (the file is not moved).

## 6. Deprecated

Deprecated = a record that was tried but is no longer a basis for current decisions. An agent that reads deprecated content is influenced by it from that moment (an instruction "do not use it as a basis" does not prevent this), so deprecation removes the original text from the working tree and stores it compressed under `.elf/deprecated/` (it can be viewed and restored). The user decides what to deprecate; the agent proposes candidates with reasons and runs `elf deprecate` after the user's instruction or approval.

- Agent reading: **unpack stored content (`elf deprecate show`) only when the user asks.**
- The goal and title of a trace stay so the session can be recognized. If either carries the withdrawn claim, change it to a neutral wording with the user at deprecation time.
- Remaining references: the handoff, the conclusion, and other documents pointing at a deprecated id are not edited by the tool; they are printed as `review:` lines for the agent to handle with the user.
- Bulk substitution: when replacing middle dots (`·`) with commas in bulk, skip the `> **Deprecated**:` lines. Their ` · ` is a field separator read by elf (the exception in the EliRule §3 typography rule).

### What the tool does
- Units = a whole session, a trial, a section, a marked block (`<!-- deprecate:begin -->` … `<!-- deprecate:end -->`), a line range (planning documents too). The log keeps only a marker line `> **Deprecated**: ID · date · unit · reason … · replaced by …` (and, for a trial, its numbered heading); the original goes to `.elf/deprecated/<ID>.md.xz`. Outputs (scripts, data, figures) stay where they are.
- View, restore, list = `elf deprecate show`, `--restore`, `list` (usage: `elf deprecate --help`). **Commit the log change and its store file together**; `elf check` checks the pairing.

## 7. Structure Migration (`elf update`)

A project in the earlier layout (blockquote headers; logs in the `2_Log/` root, `Archive/`, `Deprecated/`; `Session_Registry.tsv`) is migrated once by `elf update`. The migration is run in each project by that project's agent, which also handles the warnings.

When there are warnings, `elf update` writes nothing and creates the migration decision file `.elf/runtime/migration.yaml`. The agent looks at each item's evidence, decides the value by the criteria below, and fills it in after the user confirms (the one place inside `.elf/` filled by hand).

| Warning | Criterion | Fix |
|---------|-----------|-----|
| Header status and Registry state disagree | Judge the real state from the log body (a closing trial and a conclusion = complete, work in progress = ongoing, a deprecation marker = deprecated) | Write the value (`ongoing`, `complete`, or `deprecated`) in the decision file's `status` field |
| Neither has one | Same as above | The decision file's `status` field |
| Not a canonical value (e.g. `Active (t01 plan)`, `In Progress`) | Same as above | The decision file's `status` field |
| Link target missing | Check whether the link was already broken before the migration | Fix or remove the link (the decision file only lists it) |
| A file with the same name at the destination | Decide which one is canonical | Clean up the duplicate (the decision file only lists it) |
| git working tree not clean | — | The user commits or clears the changes, then reruns |

### What the tool does
- After the decision file is filled, rerunning `elf update` applies the migration and deletes the file when every value is valid. `elf update --dry-run` writes nothing and shows the plan and warnings. What the migration changes and the decision file format are shown by the `elf update` output and the CLI documentation (projects).
- After the migration, every PC that uses the repository needs `elf self update`.
