# AI PARA Framework & Context Management

This document defines where each kind of project document (session logs, planning
documents, scripts) states its status, and how an AI agent reads and writes documents in
each status. The rule keeps withdrawn or outdated records from being used as current fact and
gives people and the AI one shared basis for managing documents. The name comes from the
Archive concept of PARA (Projects, Areas, Resources, Archives); the rule itself is defined so
that it can be understood without knowing PARA.

## 1. Where status is stated

Each kind of document has exactly one place that states its status. No file-name prefixes,
tags, or hand-kept ledgers.

| Document | Where the status is | Note |
|------|------|------|
| Session logs (`2_Log/S/`, `2_Log/G/`) | Header `status` (`ongoing`, `complete`, `deprecated`) | Logs are not moved when the status changes (fixed paths). The list `Registry.md` is generated by elf from the headers |
| Planning documents (`1_Concept/12_Planning/`) | Folder: root = in progress, `Archive/` = closed | Location = State |
| Scripts (`61_Sim/Scripts`, `63_Analysis/Scripts`) | Folder: root = active, `Archive/` = one-off, kept | §3 |
| Deprecation (any document) | The original text is removed from the working tree and stored compressed in `.elf/deprecated/<ID>.md.xz`; a trace stays at the original position | There is no `Deprecated/` folder |

- No separate `1_Active` folder. Documents in progress stay at the root of their parent folder (`2_Log/S/`, `2_Log/G/` for session logs).
- The state folder (`Archive/`) is flat (no subfolders). File names do not change when a file moves.
- The user decides what to deprecate. The agent proposes candidates with reasons and runs `elf deprecate` only after the user's instruction or approval. Format and procedure: `.elf/managed/LogConvention.md` §6.

### 1.1 Rule documents per project language

Each project gets one set of rule documents in one language: English (`en`) projects = the English rule documents, others = the Korean ones. File names and paths are the same in every language (`.elf/managed/EliRule.md`, etc.). No separate translation (`*.en.md`, etc.) is deployed.

*   **AI behavior rule**: the AI follows the rule documents deployed in the project as the canonical rules. A version in another language is not a basis for behavior.
*   **Customization method**: write project-rule changes in **`ProjectRule.md` (user-owned, project language)** — do not edit the managed rule documents (`elf update` replaces them; an edited file gets the new version beside it as `.elf-new`).
*   **Effect**: one canonical set per project, so differences between language versions never conflict inside a project.

## 2. Status by document and when it changes

### 2.1 Session logs

| Status (`status`) | Content | AI reading |
|------|------|--------|
| `ongoing` | A session being written or edited now (e.g., `2_Log/S/S014_log.md`) | Basis for current work |
| `complete` | A closed session. A still-valid record, referred to when tracing past conclusions and paths | Reading allowed |
| `deprecated` | A withdrawn session. Only the 7 header keys and the title line remain (deprecation reason and replacement) | Only a trace; the original is in the store (§4) |

| When | Action | Tool |
|------|------|------|
| Session start | Create `2_Log/S/S###_log.md` (`2_Log/G/G###_log.md` for governance), status `ongoing`, goal recorded | `elf session new --goal` (`--gov`) |
| Writing trials | Phase 1 and Phase 2 are passed as files and written. Keep hand edits of logs to typos in content sections | `elf trial new`, `elf trial write` (LogConvention §5.1) |
| Session close | status `complete`, conclusion and user_note recorded (after user approval), `Registry.md` and the explorer setting updated. The file is not moved, so relative links stay as they are | `elf session close --from` |
| Deprecate | The original text of a whole document, a trial, a section, a marked block, or a line range is removed and stored compressed; a trace (marker line) stays at the original position | `elf deprecate` |
| Restore | Return the original text and original values from the store | `elf deprecate --restore` |

- List: `2_Log/S/Registry.md` and `2_Log/G/Registry.md` are generated by elf from the headers (session, status, conclusion or handoff). The first place a person reads for session status; do not edit them. They replace the former Session Registry (`2_Log/Wiki/Session_Registry.tsv`).
- Explorer: a VS Code file-nesting setting shows only in-progress logs expanded and folds the rest under `Registry.md` (LogConvention §1).

### 2.2 Planning documents

| Location | State | Content | AI reading |
|------|------|------|--------|
| `1_Concept/12_Planning/` root | In progress | Planning documents being written or edited now | Basis for current work |
| `Archive/` | Closed records | Original planning documents of closed work (moved under the same file name). Still-valid records | Reading allowed |

- Deprecation works as for logs (original stored compressed, a trace left). Units: whole file, marked block, or line range (planning documents have no trial or section units).

### 2.3 Wiki

| Location | Content | Updated |
|------|------|------|
| `2_Log/Wiki/` | Topic documents spanning sessions. One- or two-line summaries of the confirmed conclusions, parameters, and rules left after work finishes | In a G session after user approval (not part of the session-close procedure) |
| `1_Concept/12_Planning/Wiki/` | Planning-stage conclusions and key rule summaries | During planning work |

- Summary documents in `Wiki/` include path links to the original logs (logs stay fixed in `2_Log/S/`, so the links do not change) — when past data is needed, the original is read through that link.
- The Wiki is the summary of current facts and the first place a person reads when looking for a topic.

## 3. Scripts folder management

The Location = State rule applies to scripts inside `61_Sim/Scripts` and `63_Analysis/Scripts`.

1.  **Active Scripts**: keep the latest scripts under active development or general use at the root of the Scripts folder.
2.  **Archived Scripts**: move scripts used one-off for a specific past session under `Scripts/Archive/` (not deleted — needed to reproduce the session).
3.  **Wiki Tracking**: when moving a script to Archive, record in a `Wiki/` document — **with the path** — which session used it and for what.

## 4. Reading rules in short

| Document | Used as a basis for current decisions | Note |
|----------|----------------------|------|
| `ongoing` logs, planning root, `Wiki/`, `Registry.md` | Yes | Current state, confirmed conclusions |
| `complete` logs, planning `Archive/` | Yes (closed, still-valid records) | Tracing conclusions and paths, checking past parameters |
| Deprecation traces (`deprecated` logs, marker lines) | No | What was tried and withdrawn is known from the trace's reason and replacement |
| Deprecated originals (`.elf/deprecated/`) | No | Compressed, so they do not surface in read tools or search. Unpack them (`elf deprecate show`) only when the user asks. Restoring is the user's decision |

- When the user names a path — "open this file and summarize it" — the AI reads that file regardless of its location (deprecated originals via `elf deprecate show`).
- To use withdrawn content again, restore it with `elf deprecate --restore` first (do not unpack and copy the stored original).
